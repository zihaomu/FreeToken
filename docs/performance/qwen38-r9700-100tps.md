# Qwen3.8 Flash Next / R9700：100 tok/s 优化研究总账

更新日期：2026-11-05。目标是 **单请求、batch=1 的 decode 达到 100 tok/s，即 10 ms/token**。多请求吞吐、两张卡各跑一个实例、prefill 速度不能替代这个目标。

目前尚未达到目标。已完成的研究中，最明确的整模型改善是 scheduler/engine 共用 stream，以及选择性稠密权重 FP8。前者在同条件三轮对照中从 **22.9719 提到 34.6579 tok/s**；后者的较稳定复测为 **42.0332 tok/s、23.7907 ms/token**。仍需减少约 **13.79 ms/token**，或将吞吐提高到当前的约 **2.38 倍**。

本文是截至上述日期的核心记录，覆盖有效方法、局部加速候选、失败结论、复现参数和下一步验收。所有数字来自已保存的实验；本次文档整理没有重新运行 GPU 测量。**本次提交只归档研究文档，不包含尚未提交的实验代码、派生权重或各 worktree 的候选实现。** 文中的本地开关不能据此视为 upstream 已支持。

新增的架构深度研究集中在[第 11 节](#11-rdna4-深度研究尚未充分利用的空间)，区分源码已确认的缺口、ISA 事实与尚待实验的收益。

## 3. 已测整模型改善的细节

### 3.1 共用 stream：目前证据最充分的第一步

本地实现通过 `--scheduler-stream shared` 让 scheduler metadata 操作使用 engine stream；`separate` 仍是默认值。入口是 [scheduler.py](../../python/freetoken/scheduler/scheduler.py)、[scheduler/config.py](../../python/freetoken/scheduler/config.py) 和 [server/args.py](../../python/freetoken/server/args.py)。这些链接指向代码位置，相关实验改动不包含在本次文档提交中。

| 配置 | 三轮 decode（tok/s） | 中位数 | TTFT 中位（s） |
|---|---|---:|---:|
| separate | 22.9746, 22.9719, 22.7682 | 22.9719 | 1.41474 |
| shared | 34.6579, 34.7655, 34.6042 | 34.6579 | 1.41234 |

固定 token logits 形状为 `[32,248320]`，max error=0、KL=0；三组对应生成输出 hash 相同，MoE 计数器相同。客户端非空 SSE chunk 间隔 p95 从 45.68 降到 32.20 ms，p99 从 51.52 降到 39.98 ms。SSE 间隔不是逐 token GPU kernel 时间。

这个对照支持“在该 ROCm/R9700、batch=1 调度中，跨 stream 协作带来明显额外成本”。它没有单独证明某一个 event、硬件队列或 CPU 握手函数贡献了全部差值。

**CPU 专家握手、状态等待和结果流水继续保留。** 合并 scheduler/engine stream 不等于关闭 hybrid，也不等于程序中所有 stream 都被串行化。原有 prefill 拷贝等路径不能因这个结果被一并删除。

此前单次诊断中，两 stream 配 `GPU_MAX_HW_QUEUES=1` 达到 35.0640 tok/s，但 TTFT 为 1.72844 s；同 stream 为 34.8423 tok/s、1.42923 s。该环境变量限制 HIP 硬件队列池，不等于关闭 CPU 专家协作，也不能与 shared stream 的收益重复计算。本研究最终配置将它 **unset**，采用显式 shared stream。

### 3.2 选择性 dense FP8：减少权重流量

将 checkpoint 中选定的 **121 个 BF16 矩阵**转换成逐输出行 absmax 标定的 E4M3 权重与 FP32 scale；加载融合后对应 **85 个运行时矩阵**：

| 运行时矩阵 `[N,K]` | 次数/token | 当前 GEMV split-K |
|---|---:|---:|
| GDN fused qkvz `[16384,2560]` | 36 | 1 |
| attention output `[2560,6144]` | 48 | 8 |
| lm_head `[248320,2560]` | 1 | 1 |

专家继续 NVFP4，HC/shared/router、norm、GDN b/a 保留 BF16。激活仍为 BF16，这是 W8A16，不是 W8A8。运行时保留 FP8 存储，不先把整份权重还原成 BF16。

这些权重和 scale 从 5,801,246,720 降到 2,904,467,456 bytes，减少约 **2.70 GiB**。lm_head 独立微测为 BF16 2018.85 → FP8 1089.44 µs，延迟减少约 46.04%；这项收益已包含在 dense 量化中，不能再算作后续 native conversion 的收益。

所有完整模型轮次如下；两种配置均使用 shared stream、host embedding、7610 slots、31 workers、fetch1：

| 配置/进程 | 三轮 decode（tok/s） | 说明 |
|---|---|---|
| BF16 control | 27.6738, 35.9542, 28.8800 | 存在慢轮次 |
| FP8 first | 42.5946, 30.9814, 42.8699 | 最大 SSE 间隔约 2.299 s |
| BF16 reverse | 36.0577, 35.6819, 23.4302 | 最大 SSE 间隔约 3.527 s |
| FP8 repeat | 42.0332, 41.3961, 42.1568 | 中位 42.0332，CV 0.796%，TTFT 1.41710 s |

合计各 6 个样本的中位数为 BF16 32.2810、FP8 42.0950 tok/s，CV 分别 15.69% 和 10.44%。这些异常慢轮次全部保留；共享 host 的停顿会放大中位数比值，**不据此宣称稳定提升 30.4%**。可以确认已观测到约 41–43 tok/s 的 FP8 运行区间，仍需更稳定的成对实验确定净增益和尾延迟。

量化前预设的有限筛查为 6 prompts × 64 固定 token：聚合 top-1 agreement ≥95%、mean KL≤0.01、全部 finite。对 GPU 执行专家的参考，结果为 **97.3958%、KL 0.00501722**；同 hybrid 配置对照为 **97.65625%、KL 0.00470434**。最低单 prompt 一致率为 93.75%。这些是 logits/预测一致率，不是任务准确率、语料 perplexity 或“无损量化”证明。

### 3.3 host embedding、cache、CPU 分工

Host embedding 在同 7178 slots 下固定 logits 逐位一致，释放约 1.18 GiB。继续增加到 7610 slots 后，BF16 dense 实验仍保留 9280 个物理 KV token 容量，满足逻辑 8192 上限。额外 slots 的速度差只有约 0.30%，应主要按容量收益理解。

64-step 计数中 miss rate 为 8.56445% → 7.82552%，CPU experts/layer 为 0.25716 → 0.23014；两次自然生成的路由历史不同，不能把差异完全归因于 cache。改变 cache 会改变 CPU W4A8 与 GPU W4A16 的分工：7178→7610 的 32-token 对照 top-1=100%，但 KL=0.00105081，已经不是逐位相同。

同一轮 wide-NUMA、固定 fetch1 的线程对照：

| CPU workers | 三轮 decode（tok/s） | 中位数 | 平均活跃 CPU cores |
|---:|---|---:|---:|
| 8 | 34.8792, 34.6545, 32.0704 | 34.6545 | 10.02 |
| 16 | 35.7458, 35.5368, 35.5532 | 35.5532 | 18.01 |
| 31 | 35.9390, 35.9169, 35.8030 | 35.9169 | 32.94 |

31 workers 比 16 workers 约快 1%；这不足以宣称 31 对所有主机最优。Offload 对照为 34.0297/26.7495/27.8684 tok/s，波动明显，不能据它断言稳定的 hybrid 百分比收益。CPU/NUMA 资源压力曾产生约 14 tok/s 的异常组，必须保留而不能归入 kernel 退化。

在 [nvfp4_fused_moe.py](../../python/freetoken/kernel/triton/nvfp4_fused_moe.py) 的本地实现中，负 slot 在读取权重前退出，避免 CPU-owned route 被 clamp 成 slot 0 后仍在 GPU 重算。原本“没有 CPU route 时不通知 CPU”的 publish 快路已存在，不能算本次新增成果。

| inactive routes / top-10 | 原链（µs） | 提前退出后（µs） |
|---:|---:|---:|
| 0 | 58.161 | 58.455 |
| 1 | 53.885 | 55.466 |
| 2 | 49.934 | 48.790 |
| 10 | 40.032 | 11.017 |

常见 0/1 条 CPU route 时没有收益，全 inactive 才明显下降。31-worker graph 探针中 0/1/2 个 CPU expert 约为 8.53/109.25/199.54 µs；仍存在固定协作成本。后续必须按真实 CPU route 分布优化，不能删除正确性所需的 publish/wait，也不能把全 inactive 加速外推到完整模型。

这里的“加权节省”是形状微测时间乘以每 token 调用次数，**不是 profiler 测得的整模型增益**。除单独说明外，候选均默认关闭，未计入 42 tok/s 基线。

| 方向 | 局部实现/实测延迟 | 加权节省或局部改善 | 当前验收结论 |
|---|---|---|---|
| 01 HC | BF16 专用 GEMV；down+SiLU、up+gate-mix；接入已有 combine+norm；完整调用边界 4.012933 → 3.061207 ms/token | 微测外推省 0.951726 ms，-23.72%；独立 A/A 最大漂移约 0.37% | 整模型数值未过，不进入整模型性能验收 |
| 02 FP8 dense | 原生 FP8 upcast + split-K=1 输出融合；85 矩阵加权 5.3700 → 5.1477 ms | 省 0.2223 ms，-4.14% | 算子数值/graph 通过；未达 10% kernel 门槛，独立 A/A 与模型待测 |
| 03 NVFP4 routed MoE | gate/up+SiLU 融合及 tile/warps；全 GPU route 完整链 59.083 → 55.889 µs | 最优约 -5.41%；机械乘 48 为 0.153 ms | 数值通过；活跃 route 未达门槛，缺独立 A/A 和模型验收 |
| 04 shared expert | BF16 gate/up GEMV+SwiGLU、down GEMV；27.0931 → 20.3105 µs | 48 层外推省 0.325565 ms，-25.03%；A/A 最大约 0.22% | 整模型数值未过，不进入整模型性能验收 |

| 06 QSA QKV | QKV 114.599 → 109.415 µs；index projection 8.864 → 7.301 µs | 12 层加权 1.4816 → 1.4006 ms，省 0.0810 ms，-5.46% | 算子/graph 通过；微测缺完整 A/A，模型未测 |
| 07 QSA attention | merge 按 D 分块，D64 减少 scratch；7936 context 的主核+merge 14.274 → 12.757 µs | 该子链 -10.63%，A/A 约 0.17% | 局部数值容差与 graph 通过，非逐位；整模型待测 |
| 07 GDN recurrence | BV/warps 离线编译筛选 | 只有寄存器/scratch 证据，没有 GPU 加速结果 | 尚无可采用性能结论 |

HC 的完整微测边界为 48 次 mix336 + 48 次 transition336 + 48 次 combine + 1 次 mix320；不能再把 transition 内的 combine/norm 收益重复相加。Shared 另一轮的 36.6533 µs 慢样本保留；纳入该轮样本时平均改善约 21.21%，不能只展示最快一轮。

FP8 dense 的两项增量需要分开归因：

| `[N,K]` / 次数 | 原 FP8 路径（µs） | 仅 native upcast | native + epilogue |
|---|---:|---:|---:|
| `[16384,2560]` / 36 | 77.194 | 74.602 | 72.012 |
| `[2560,6144]` / 48 | 31.305 | 30.981 | 30.980 |
| `[248320,2560]` / 1 | 1088.458 | 1082.198 | 1068.249 |

仅 native 加权省 0.1151 ms；epilogue 再省 0.1072 ms。37 次 split-K=1 可省独立归约，48 次 split-K=8 不能直接删除跨 K 归约。原生转换没有进一步减少权重字节数，因此不能重现 BF16→FP8 的量化收益。这里的逻辑权重带宽也不是硬件 DRAM 计数器，不能据此宣称整卡已打满带宽。

NVFP4 微测用 355.86 MB 轮换权重；inactive=1 最好 -6.55%，inactive=2 最好 -4.57%。全 inactive 的 20–27% 改善不代表生产路由。方向 02 的原生 scale 转换也没有自动集成进方向 03；必须分别测 A、A+D、A+D+B，不能归到 gate/up 融合名下。

QSA merge 在 64 splits 的离线资源由 VGPR256/private56 bytes 降到 D64 的 VGPR96/private0。单独 merge 为 5.250→3.595 µs；完整主核+merge 在 512/2048/7936 context 分别改善 7.29%/8.90%/10.63%。这些时间不含 QKV、score/top-k、index/compression；selection budget 仍为 2048。KV 轮换分配超过 256 MiB，但实际选中的子集不一定超过缓存，不能称为已证明的 DRAM 冷读。

方向对应的本地分支为 `perf/qwen38-r9700/<方向>-20261105`，方向依次是 `hc`、`fp8-dense`、`nvfp4-moe`、`shared-expert`、`router`、`qsa-qkv`、`gdn-qsa`。实现仍在各自 worktree，分支 HEAD 本身不包含未提交候选。

候选开关索引，仅用于定位已有实验实现：`FREETOKEN_RDNA4_HC`、`FREETOKEN_RDNA4_SHARED`、`FREETOKEN_RDNA4_ROUTER_GEMV`、`FREETOKEN_RDNA4_FP8_UPCAST`、`FREETOKEN_RDNA4_FP8_GEMV`、`FREETOKEN_ROCM_NVFP4_FUSED_SILU`、`FREETOKEN_RDNA4_QSA_GEMV`、`FREETOKEN_QSA_MERGE_TILE`。具体取值/目标架构限制应以对应候选源码为准。

## 6. 精度边界、upstream 来源与最新 AsmEvo 结论

### 6.1 “旧 GEMV＋融合”指本地候选

基础实现是 [unquantized.py](../../python/freetoken/layers/quantization/linear/unquantized.py) 中的 `UnquantizedLinearMethod → TorchLinearKernel → F.linear`。ROCm trace 中这些投影命中 BF16 输入/输出、FP32 compute 的 BBS 矩阵 kernel；不能把基础实现称为此前已经存在的专用 Triton GEMV。

本地 `_bf16_gemv_kernel` 读取 BF16 后做 FP32 乘法/归约，再存 BF16。两种实现的名义精度相同，但归约和最终舍入不保证逐位一致。[hc.py](../../python/freetoken/kernel/triton/hc.py) 中的 `hc_combine_norm` 已在基础源码存在；本地研究新增的是部分调用链的接入，不能将该 kernel 本身列为新发明。

### 6.2 同权重模型门槛与量化门槛不同

七方向算子替换预先规定：32-token 初筛，随后 6 prompts × 64 token；聚合 top-1 agreement ≥99%、mean KL≤0.001、finite。这个门槛比新增权重量化的 95%/0.01 更严格，不能为了通过某个失败候选临时切换门槛。

| 同权重候选 | top-1 一致数 / 384 | 一致率 | mean KL | 结论 |
|---|---:|---:|---:|---|
| 独立进程 A/A | 384 | 100% | 0 | 含初筛共 416 个位置 logits 逐位一致 |
| HC fused | 378 | 98.4375% | 0.000971868 | 不通过 |
| HC GEMV-only | 377 | 98.1771% | 0.001114404 | 不通过 |
| HC combine-only | 379 | 98.6979% | 0.000799506 | 不通过 |
| shared fused | 378 | 98.4375% | 0.000941489 | 不通过 |
| router GEMV | 381 | 99.21875% | 0.000547941 | 聚合门槛通过；不是 bitwise |

Router 整模型自然生成中，512/256 为 42.405→43.120 tok/s，2048/256 为 42.288→42.887；表观 +1.69%/+1.42%，置信区间跨零，而且 12/12 对应 A/B 输出发生分叉。固定 token 历史后，分别为 **42.2494→41.4086（-1.99%）**、**42.1645→42.6261（+1.10%）**；条件 95% 区间为 [-23.463%,+7.101%]、[-5.135%,+11.109%]。8 次启动、48 个正式请求仍未证明稳定收益。

这些实验保留了秒级停顿，原因未收口，不能直接归咎于 PLE I/O、CPU 握手或某个监控接口。当前状态为 `quality_pass / performance_inconclusive`。

### 6.3 AsmEvo：本轮没有候选被接受

本轮使用 source mode 对 Triton 源码做单项修改、编译与外部正确性/性能检查，不是手写 AMDGCN 改写。真实输入捕获的 32-token logits、token、路由、计数器与原模型逐位一致。

| 方向 | 最新尝试与实测 | 决策 |
|---|---|---|
| HC | 首窗口遭外部 GPU 占用；重试基线 35 cases 通过，但计时 CV=3.5533% 超过 3% 门槛 | 新融合候选未编译/验收/计时，不能报告加速 |
| shared | 保持 `F.linear`，只改 SwiGLU 的 sigmoid 表达式；34 cases 含 graph 新输入逐位通过；27.6210→27.6328 µs | 无收益；ISA 中昂贵 division 序列仍在 |
| router | 保持 `F.linear`，Top-10 静态展开改运行时循环；307 cases 通过；13.0340→13.4684 µs，基线 CV=10.608% | 计时不稳定，不通过；不能用指令数下降代替性能通过 |

Router 指令数从 2532 降到 1001、函数字节从 17812 降到 6208，仍没有形成通过验收的加速。Shared 的 VGPR 从 34 增到 35，除法相关指令数量未减少。两者说明“源码更短/指令更少”不是采用依据。

真实输入诊断将旧 GEMV 的差异定位到投影输出的 BF16 舍入边界；例如 router 240×512 logits 中 15 个值不同，分布在 14 个 case。FP64 参考在部分边界上反而更接近本地 GEMV，因此不能简单称为数学计算错误，但它确实改变了既有模型行为。HC combine-only 的模型差异尚未定位：25 个已捕获局部 combine/norm case 逐位相同，不能把原因强行归为同一种投影误差。

最终 accepted candidates=0，未替换生产路径，也没有本轮新候选的完整模型速度结果。

## 7. 其他方法及停止重复尝试的理由

| 方法 | 已有证据 | 决策 |
|---|---|---|
| pinned PLE | prefill 模式 35.2136→35.3918 tok/s，约 +0.51%；TTFT 1.40825→1.45484 s；常驻表约 47.7 GiB | 继续用 disk；all 模式还有 19.32 tok/s 慢轮次 |
| 仅限制 HIP 硬件队列 | decode 接近 shared，但历史单次 TTFT 明显更差 | 不作为 shared 之外的额外收益，不全局设置 |
| router tuple/defer Top-10 | 旧局部尝试回退约 16.22–34.66% | 拒绝这些变体，保留原 Top-10 语义 |
| QSA QKV 进一步 FP8 | 只读容量估算可额外节省 408,305,664 bytes | 尚未量化实现/质量验收/测速，不能记为有效加速 |
| GDN BV/warps | BV8/w1、BV16/w1、BV32/w2 有较低 VGPR；BV128/w4 明显 spill | 仅用于缩小实验范围，不宣称性能改善 |

较早的 **FP8 KV** 研究属于另一模型/实现阶段，可以保留其价值，但不能加入 Qwen3.8 的 42 tok/s 账目。Qwen3.6-35B-A3B BF16 权重、serial 调度下，每档 5 轮的同候选分支对照为：

| 输入长度 | BF16 KV decode | FP8 KV decode | 吞吐变化 |
|---:|---:|---:|---:|
| 512 | 41.211 | 41.116 | -0.23% |
| 8192 | 40.150 | 42.129 | +4.93% |
| 32768 | 40.873 | 42.183 | +3.21% |

此前 D128 的 gfx1201 专项还验证了两种实现选择：GQA4/8 用四字节打包 FP8 读取、原生转换和 NT 读取提示，采用 64-key/1 stage/2 warps；GQA2 保留更快的兼容展开与 32-key/1 stage/2 warps，消除写入 scratch 的 spill。打包路径要求地址与 stride 满足对齐条件；其他合法布局回退。这些资格限于当时测过的形状和工作负载，不能直接推广到本模型 GQA12/D256 的 QSA 路径。

## 8. 后续实验统一口径

1. **固定参照。** 保存实际源码树、candidate patch、环境/模型 hash；确认实际 import 与 kernel dispatch。变更环境或 CPU/NUMA 布局时同时重测 A/B。
2. **先数值和状态。** 用独立 reference 与真实激活，记录中间 BF16 边界；graph replay 包含输入变化。影响 recurrent/cache 时验证 prefill→decode、连续更新、reset/reuse。保持既有测试容差，不将 skipped 当 passed。
3. **再微测。** 至少 3 个独立预热批次，每批至少 100 次调用；短 kernel 成组计时；做同配置 A/A。权重工作集轮换至少 256 MiB，并保留热缓存对照；GDN state 使用真实复用方式。
4. **最后整模型。** A→B 和 B→A 独立启动，每进程预热后至少 3 个正式请求；固定历史与自然生成分别报告。保存 decode、TTFT、p95/max SSE 间隔、CPU/GPU route 数、miss、频率、内存和资源竞争。
5. **按预设门槛决定。** 同权重 `kernel_pass` 需局部数值通过、加权延迟下降至少 10% 且超过 A/A 波动；`model_pass` 需模型数值通过、目标 decode 中位提升至少 1%、配对收益 95% 区间下界大于 0，TTFT/p95 不回退超过 3%。方向 07 长上下文另有 2% 目标。统计不确定就保留 inconclusive。
6. **组合重新验收。** 单项通过不保证组合通过。量化与同权重算子分别使用已声明门槛；384-token screen 不替代正式任务质量或生产稳定性。全部慢轮次、资源冲突和失败记录保留。

五步阶段此前定向测试共 64 passed：CPU-MoE/scheduler 28、PLE 6、NVFP4 decode 4、FP8 linear/loader 26。这是历史验证记录，不是本次文档修改重新跑出的结果，也不代表完整仓库或 NVIDIA 回归通过。

## 9. 通往 100 tok/s 的下一阶段

首先保持 shared stream、host embedding、disk PLE、受限 fetch 的 hybrid，以及当前 selected-dense FP8，建立不受秒级停顿干扰的新对照；42.0332 是历史实测，不是换设备后可直接使用的基线。

随后优先解决 HC/shared 的数值验收：局部节省较大，但未经模型门槛不能采用。需要保留 BF16 运算边界，分别定位投影、激活、gate-mix、combine/norm，避免一次改多项。Router 已完成一轮模型验证，下一步重点是可信的成对计时和相同 route 历史，而不是继续累计微测百分比。

FP8 native/epilogue、NVFP4 gate/up 融合、QSA merge 可作为后续增量研究，但目前的绝对微测节省远小于 13.79 ms。即使组合后实际每 token 减少 1/3/5 ms，按 42.0332 tok/s 换算也仅为约 43.88/48.10/53.22 tok/s；这是延迟预算示例，不是性能预测。

因此达到 100 tok/s 还需验证更大的改动：更多高流量权重的量化与质量评估、真正支持本模型的 TP、或能复用权重读取的 MTP/推测执行。当前均无通过验收的收益，不能承诺单靠 tile/warp 调整达到目标。新增路线应独立建基线，再按第 8 节验收。

## 11. RDNA4 深度研究：尚未充分利用的空间

### 11.1 优先级与可以证伪的最小实验

| 次序 | 尚未充分利用的点 | 直接证据 | 最小实验 / 决定是否继续的依据 |
|---|---|---|---|
| 1 | 把 FP8 释放的 VRAM 用于当前 workload 的有效工作集 | KV 从 8768 扩到 124544 tokens，expert slots 仍 7610，逻辑长度只允许 8192 | 固定 KV 需求后扫描专家 slots +256/+512/+768；看真实 miss、CPU-active layers、decode，而非只看显存占用 |

| 4 | RDNA4 packed vector 算术 | 已归档本地 BF16 GEMV 使用 FP32 mul/FMAC，未见 BF16 DOT2；FP8 native 用标量转换 | 独立尝试 BF16 DOT2、成对 FP8 upcast，保留运算边界；检查生成 ISA、真实数值和完整链 |

### 11.2 显存预算：量化收益还没有完全用于降低 miss

两份实际日志给出：

```text
E/step5-bf16-hybrid-control/server.log
  Allocating 8768 tokens for KV cache, K + V = 0.21 GiB
E/step5-fp8-hybrid-repeat/server.log
  Allocating 124544 tokens for KV cache, K + V = 2.94 GiB
```

参数同时固定 `--moe-cache-size 7610`、`--max-running-requests 1`、`--max-seq-len-override 8192`、`--cache-type naive`。在这个目标负载里，新增的大部分 KV 容量用不上。这是固定 cache 配置没有重新利用容量的事实，**不是宣称 FreeToken 没有自动显存规划能力**。

[engine.py](../../python/freetoken/engine/engine.py) 的 KV 初始化将剩余预算交给 `solve_num_pages`；同文件 `_resolve_auto_moe_cache_size` 已能先保留 KV 再填专家。[cache_budget.py](../../python/freetoken/engine/cache_budget.py) 和 CLI 已提供 `--moe-cache-auto`、`--kv-reserve-tokens`、`--num-tokens`/`--num-pages`。优先复用这些入口；auto 的 reserve 是下限，显式 expert size 与 auto 需要按互斥规则切换，不能简单把所有参数叠上去。

以已核验的 2,896,779,264 bytes 权重节省、每个专家 slot 2,780,160 bytes 计算，理论上相当于 **1041 个完整 slot** 的字节预算，未扣除其他开销。它不是可直接启动的保证值。先保留满足完整 8K 请求及必要暂存的 KV，再试 +256/+512/+768 slots，并检查真实分配和 prefill workspace。

7610→更多 slots 是否有效，取决于路由工作集；先前 +432 slots 只观察到约 0.30% 差异，故不预报百分比。CPU/GPU 分工变化还会触发 W4A8/W4A16 数值差异，必须复测质量。

### 11.3 Hybrid 分工缺少小 miss 的成本曲线

源码已包含 recency、带宽校准和 overlap，不应重复提出“从零加入”。真正缺口在校准与生产负载不完全一致：

- [benchbw.py](../../python/freetoken/moe/benchbw.py) 的 `_cpu_moe_step_fns` 每次让 CPU 执行 `top_k` 个专家；本模型为 10。`measure_overlap_bw` 让 CPU 与整层 gather 持续并发，测饱和带宽。
- [bench_profile.py](../../python/freetoken/moe/bench_profile.py) 的 `fetch_fraction` 使用 `pcie_ov/(pcie_ov+cpu_ov)`；[offload_kernels.py](../../python/freetoken/moe/offload_kernels.py) 的 min-wait 取整比较比例成本，未显式加入固定发布、收尾、少量专家启动开销及 GPU expert 执行时间。
- 实际较稳定 FP8 窗口仅约 **0.32975 CPU experts/layer**。已有 graph 探针 0/1/2 专家约 **8.53/109.25/199.54 µs**。把 top-10 的 GB/s 直接缩到 1 个专家没有保证。
- 目前速度基线显式固定 fetch1，因此自动策略的改进还没有进入这组结果；需要将新策略与 fixed-fetch1 对照。

建议用完整链实测表求每个 miss 数的最优整数分工，而不是只改一个比例：

```text
T_layer(f) ≈ T_ensure + T_publish
           + max(T_cpu(m-f), T_copy(f) + T_gpu(active GPU routes) + T_shared)
           + T_wait/combine
```

这是安排 shared 重叠后的成本示意，实际用 graph 包围整个链计时，避免重复计入探针已包含的 handshake。`f` 的决策还应考虑被 fetch 专家后续复用的价值；只优化本层当前 token，可能让缓存失去收益。

新的校准表至少按 GPU/PCI、CPU ISA、worker 数、CPU affinity/NUMA、kernel/编译器版本隔离。现有 profile 已保存部分这些信息，下一步应检查匹配与失效策略，不能笼统称它没有硬件校准。

### 11.4 单 stream 内仍可让更多工作与 CPU 并行

[qwen4_exp/moe.py](../../python/freetoken/models/qwen4_exp/moe.py) 当前顺序为 router projection → shared expert → shared gate → routed experts → shared merge；[layers/moe.py](../../python/freetoken/layers/moe.py) 的 `_decode_hybrid` 内才执行 ensure → CPU publish → copy_missing → GPU experts → CPU wait/combine。

因此 shared expert 已经结束时，CPU 专家才开始。这与“已经合并 scheduler/engine stream”是不同层面的优化机会。可保持同一 GPU stream，将 routed 路径拆成 prepare/finish：

```text
当前：router → shared/gate → route/ensure/publish → fetch/GPU experts → wait/combine
候选：router → route/ensure/publish → shared/gate → fetch/GPU experts → wait/combine
```

shared/gate 必须仍在可能原地覆盖 `hidden_states` 的 routed GPU kernel 前求值；保留唯一 expert ID、分工、BF16 舍入与 publish/wait 顺序。不要先引入第二条 compute stream。

忽略公共开销时，原成本 `S + max(C,G)` 可变成 `max(C,S+G)`；理论节省为 `min(S,max(C-G,0))`。只有 CPU 暴露在关键路径上才有收益。按每层 shared 微测约 27 µs、平均 0.33 个 CPU expert，若每个发生 CPU 的层都完全隐藏 shared，粗略上限也只有约 **0.43 ms/token**；实际还可能更低。这是机会边界估计，不是新测速。

### 11.5 真正值得进一步研究的原生指令

RDNA4 ISA 提供 `V_DOT2_F32_BF16`、`V_DOT4_F32_FP8_FP8` 和 `V_CVT_PK_F32_FP8`。本次检查已归档的 5 份 HC/shared 本地 BF16 GEMV JIT assembly，均未发现 DOT2/WMMA，使用 FP32 mul/FMAC；这只描述这些本地候选，不能推广成 upstream BLAS 未用原生指令。[AMD RDNA4 ISA：Packed Math / Conversion](https://docs.amd.com/v/u/en-US/rdna4-instruction-set-architecture)

具体分开试三条路线：

1. BF16×BF16 的 HC/shared 用成对输入的 BF16 DOT2→FP32 累加，检查是否减少展开、寄存器和指令压力。归约/舍入可能变化，仍必须过第 6 节门槛，不能因名义 dtype 相同视为无损。
2. FP8 W8A16 保持 BF16 激活，只试成对 FP8→FP32 转换和相应寄存器布局。它不改变权重流量，优先验证是否处于关键路径。
3. FP8 DOT4 或 FP8 WMMA 需要匹配输入格式。将 BF16 激活转 FP8 属于新 W8A8 量化，另做质量验收；不能当作现有 W8A16 的透明替换。

**对“缺少打包读取”的重要修正：** 非特化离线 probe 的 ISA 有 64 条 byte load，但实际 `02-fp8-dense/triton-gpu` 中，对齐的运行时特化已经出现 `buffer_load_b128`，不能用通用 stride probe 推断生产路径只读单 byte。10 份运行时产物中仍有非对齐/尾部使用 byte load 的变体，应匹配实际形状与 dispatch 后分析。

对齐变体的 native 路径仍可见 64 处标量 `v_cvt_f32_fp8` 静态指令，约 96–97 VGPR、scratch=0；同时存在 LDS layout 操作。它说明“成对转换/布局”是可检验的方向，不证明它比原软件解码更快，更不能把静态指令计数当动态成本。

NVFP4 decode 早已使用 int32 权重读取、较宽激活读取和延迟 K 归约，见 [nvfp4_fused_moe.py](../../python/freetoken/kernel/triton/nvfp4_fused_moe.py)。这些不能再作为尚未开发的新方案。当前它仍解包 E2M1、展开 scale 后做向量计算；RDNA4 公布的 4-bit 矩阵类型是 **IU4**，不能据此宣称可原生直算 NVFP4/MXFP4。换 checkpoint 编码也不自动获得矩阵加速。[AMD 的 RDNA4 WMMA 类型/速率表](https://gpuopen.com/learn/accelerating_generative_ai_on_amd_radeon_gpus/)

### 11.6 Tile、split-K 与缓存层次还没有统一适配

[fp8_pertensor_linear.py](../../python/freetoken/kernel/triton/fp8_pertensor_linear.py) 固定 `BLOCK_N=16`、`BLOCK_K=128`、`num_warps=1`，依据 `1536 // n_tiles` 选择 split-K。三个真实形状对应：

| `[N,K]` | N tiles | split-K | 主核工作块数 |
|---|---:|---:|---:|
| `[16384,2560]` | 1024 | 1 | 1024 |
| `[2560,6144]` | 160 | 8 | 1280 |
| `[248320,2560]` | 15520 | 1 | 15520 |

GDN 和 lm_head 已有大量 N 并行度；output projection 的 split=8 需要完整 chain 重新评估。还可研究避免每个 K tile 都先做横向归约，代价是增加活跃 accumulator。之前 native/epilogue 轮次没有完成这些维度的调优。

硬件口径也要统一：AMD 表列 R9700 为 64 CU、8 MiB L2、64 MiB Infinity Cache；本地 Torch 设备记录 `multi_processor_count=32`，不可直接当作 CUDA SM 数或断言只用了半卡。LDS 官方表的容量与单 block 可用上限也不能互换，launch 应查询实际属性并结合 CU/WGP 模式和编译资源解释。[AMD ROCm 10.1 GPU 规格](https://rocm.docs.amd.com/en/docs-10.1.0/reference/gpu-specs.html)

[qsa/attend.py](../../python/freetoken/kernel/triton/qsa/attend.py) 的 split/tile 注释明确来自 GB300；AMD 分支主要在 LDS 不足时缩 KV tile。这解决可运行性，但没有完成 RDNA4 最优分块。已试的 D64 merge 只覆盖收尾，仍可联合调主核 block_n、split 数、warps 与 merge。短上下文的绝对占比小，保持后置优先级。

另一个尚未完整评估的变量是 GFX12 temporal hint：区分流式 dense 权重、刚写入又立即使用的专家 slot、当前层 state/activation，避免一律套 NT。LLVM 定义了 regular、non-temporal、high-temporal 及分别作用于近端缓存/MALL 的组合；这些是 hint，不保证驻留，更不能把 `.cg` 的 NVIDIA 直觉直接套用。[LLVM GFX12 指令 modifier](https://llvm.org/docs/AMDGPUModifierSyntax.html)

AMD 的 RDNA4 WMMA 指南还展示了延伸 K 来实现低精度 128-bit 加载、寄存器内衔接两个 GEMM 的方法，可用于 prefill 或 MTP verify 的设计。现有 M=1 GEMV 已有宽加载，不能直接照搬指南中的 GEMM 收益；HC 的 336 维中间层、shared 的 640 维还涉及跨 tile/CTA 依赖与 BF16 边界。[WMMA guide part 2](https://gpuopen.com/learn/wmma-guide-amd-rdna-4-gpus-part-2/)、[part 1](https://gpuopen.com/learn/wmma-guide-amd-rdna-4-gpus-part-1/)

### 11.7 MTP 比继续压缩单个 M=1 kernel 更有结构性空间

当前 checkpoint index 有 **3101 个 `mtp.*` tensor 名称**，源码有 [Qwen4ExpMTPDraft](../../python/freetoken/models/qwen4_exp/mtp.py)、[MTP proposer](../../python/freetoken/spec/mtp/proposer.py) 和 [verify contract 测试](../../tests/spec/test_verify_contract.py)。这确认实现与权重入口存在，**不代表这份 NVFP4 checkpoint 已在 R9700 完成 draft 加载或性能验收**。Loader 对具体 expert 格式、draft 精度和显存的约束还需先验证。

在 batch=1、一次只生成一个 token 时，GEMV 很难复用整个模型权重。若一次 target verify 能处理多个 proposal，就有机会把部分权重读取成本摊给多个已接受 token，并为 WMMA 提供更有用的 M 维。矩阵指令的存在本身不保证 M=1 更快。[AMD RDNA4 WMMA 布局与 16×16 运算说明](https://gpuopen.com/learn/using_matrix_core_amd_rdna4/)

验收指标应是：

```text
accepted tokens/s = E[每轮最终提交 token 数]
                    / E[T_draft + T_target_verify + T_reject/state_commit + T_调度]
```

同时记录接受率、有效 proposal 长度、GDN state rollback、QSA metadata、graph 重放、CPU 专家 M>1 路径、draft 额外 KV/专家显存及 TTFT。不能只测 verify kernel，也不能将 proposal tokens 当生成吞吐。先用原权重验证，再单独加入 dense FP8，避免把 draft/target 数值差异与 kernel 回归混在一起。

### 11.8 测量能力与架构适配的最终边界

已有 synthetic stream 对照中，full-dense 的 single/dual 约为 22.06/22.05 ms，PLE/copy 等 toy 对照也未复现完整服务的巨大损失。因此现有证据支持优化 FreeToken 的具体依赖图，**不支持“RDNA4 所有双 stream 都慢”**。单 stream 是当前模型有效配置，不能升级成全框架禁止并行的架构原则。

约 42 tok/s 对应 23.79 ms/token；粗略逻辑权重模型为 7.08 GB/token。按标称 640 GB/s 相除是 11.06 ms，但这忽略 CPU 分担、缓存命中、读写放大和同步，既不是实测 DRAM 带宽，也不是严格性能下限。它仍提示：要接近 10 ms，必须同时减少流量和等待，不能依赖把 CPU、GPU 利用率数字都拉高。

新测量先枚举锁定 ROCm 环境实际支持的 counters。官方 ROCprofiler-SDK 将 gfx1200/1201 的 thread trace 标为 **trace-only**，不支持该路径的 `--att-perfcounters`；不要照搬 Instinct 配方。使用可用的普通 PMC、有限 kernel 的指令 trace、事件时间和 host 时间线交叉验证，性能计时与 profiler 分开。[ROCprofiler thread trace 支持表](https://rocmdocs.amd.com/projects/rocprofiler-sdk/en/latest/how-to/using-thread-trace.html)、[ROCm profiling 工具选择](https://rocm.docs.amd.com/en/docs-10.1.0/components/profiling-tools-selection.html)

代码层面建议逐步建立明确的 gfx1201 能力/成本配置：FP8 转换能力、DOT/WMMA 类型、运行时 graph/memop 探针、shape tile、cache hint 分开描述；使用实测表决定路径，避免一个 `is_hip` 或“支持 FP8”开关包办所有决策。当前 HIP signal allocation、graph memop 探针、无 CPU route 快路已经存在；后续优化保留这些正确性基础。
